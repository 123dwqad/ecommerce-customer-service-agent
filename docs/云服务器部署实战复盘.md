# Agent 项目云服务器部署实战复盘

这份文档不是通用教程，而是基于这次真实部署过程整理的“学习版复盘”。

它适合你以后复习这些问题：

- 一台新云服务器从哪里开始
- Docker 和 `docker compose` 到底怎么用
- 遇到拉镜像超时、装依赖超时、容器启动失败时怎么排查
- 为什么本地能跑，上云后还会有一堆问题

---

## 1. 这次部署的目标

把本地的 Agent 项目部署到云服务器，并通过公网访问。

项目最终采用的结构：

- `api`：FastAPI 后端
- `mcp`：MCP 工具服务
- `redis`：短期记忆 / 会话缓存
- `nginx`：静态前端托管 + 反向代理
- `data/`：SQLite 数据持久化
- `data/rag_qdrant/`：电商知识库 Qdrant 向量库持久化

最终访问方式：

```text
http://服务器公网IP/
```

## 4. 实际操作过程

## 4.1 登录服务器

登录成功后，终端提示符类似：

```bash
root@iZ2mjpr024qg4hZ:~#
```

这说明已经进入 Linux 服务器。

先确认系统：

```bash
cat /etc/os-release
```

查看资源：

```bash
free -h
df -h
```

---

## 4.2 安装 Docker

一开始尝试使用 Docker 官方仓库安装：

```bash
apt update
apt install -y ca-certificates curl gnupg git
install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://download.docker.com/linux/ubuntu/gpg | gpg --dearmor -o /etc/apt/keyrings/docker.gpg
chmod a+r /etc/apt/keyrings/docker.gpg
```

但后续 `apt update` 访问 Docker 官方源握手失败，导致 `docker-ce` 相关包无法安装。

于是改用 Ubuntu 自带 Docker：

```bash
apt update
apt install -y docker.io docker-compose
systemctl enable --now docker
```

验证命令：

```bash
docker --version
docker-compose --version
systemctl status docker --no-pager
```

当时看到的结果说明：

- Docker 已安装
- `docker-compose` V1 也装好了
- Docker 服务已启动

---

## 4.3 安装 Compose V2

后面遇到一个关键兼容问题：

```text
KeyError: 'ContainerConfig'
```

这不是项目代码问题，而是旧版 `docker-compose` V1 和当前 Docker 引擎的兼容问题。

最终安装 Compose V2：

```bash
apt update
apt install -y docker-compose-v2
docker compose version
```

安装后确认版本：

```text
Docker Compose version 2.37.1+ds1-0ubuntu2~22.04.1
```

从这一步开始，后续命令统一使用：

```bash
docker compose ...
```

不再使用：

```bash
docker-compose ...
```

---

## 4.4 上传项目到服务器

因为项目在本地电脑，不在 Git 仓库，所以采用“压缩包上传”的方式。

本地 PowerShell：

```powershell
cd D:\ChunZhao\Agent

Compress-Archive -Path `
app,frontend,mcp_server,skills,deploy,docs,`
pyproject.toml,poetry.lock,Dockerfile,docker-compose.yml,`
.dockerignore,.env.prod.example `
-DestinationPath "$env:USERPROFILE\Desktop\agent-deploy.zip" -Force
```

再上传到服务器：

```powershell
scp "$env:USERPROFILE\Desktop\agent-deploy.zip" root@服务器IP:/opt/
```

服务器上解压：

```bash
apt install -y unzip
mkdir -p /opt/agent
unzip -o /opt/agent-deploy.zip -d /opt/agent
cd /opt/agent/Agent
ls
```

这里要特别注意：

- 解压后目录多了一层 `Agent/`
- 所以真正启动目录是：

```bash
/opt/agent/Agent
```

不是：

```bash
/opt/agent
```

---

## 4.5 创建生产环境变量

项目启动需要 `.env.prod`，而不是只有 `.env`。

创建方式：

```bash
cd /opt/agent/Agent
cp .env.prod.example .env.prod
nano .env.prod
```

至少要补这些配置：

```env
DASHSCOPE_API_KEY=你的真实Key
ZHIPU_API_KEY=你的真实Key
TTS_VOICE=longxiaochun
```

这里学到一个重要点：

- 本地 `.env` 不等于服务器生产环境配置
- 服务器应该有自己的 `.env.prod`
- 不要把真实密钥提交到仓库

---

## 4.6 首次启动 Compose

在项目目录执行：

```bash
cd /opt/agent/Agent
docker compose up -d --build
```

然后检查：

```bash
docker compose ps
docker compose logs -f api
```

不过首次启动并没有一次成功，后面开始进入排障阶段。

## 5. 这次部署遇到的问题与解决方式

这一部分最重要，因为真实部署最有价值的就是排障能力。

## 5.1 问题一：Docker Hub 拉镜像超时

报错类似：

```text
Get "https://registry-1.docker.io/v2/": context deadline exceeded
```

出问题的镜像：

- `redis:7-alpine`
- `nginx:1.27-alpine`
- `python:3.12-slim`

### 原因

国内服务器访问 Docker Hub 很不稳定。

### 解决方式

把镜像改成 DaoCloud 公共镜像站。

修改后：

- `docker-compose.yml`
  - `redis:7-alpine` 改成 `docker.m.daocloud.io/library/redis:7-alpine`
  - `nginx:1.27-alpine` 改成 `docker.m.daocloud.io/library/nginx:1.27-alpine`
- `Dockerfile`
  - `FROM python:3.12-slim` 改成 `FROM docker.m.daocloud.io/library/python:3.12-slim`

这一步学到的能力：

- 会识别镜像拉取问题
- 会换镜像源而不是反复重试

---

## 5.2 问题二：Dockerfile 中 `apt-get update` 卡住

当时 Dockerfile 里有安装 `curl` 的步骤，容器构建时在这一步速度很慢。

### 原因

基础镜像内部再跑系统包更新，会受到 Debian 源网络影响。

### 解决方式

移除 Dockerfile 中不必要的 `apt-get install curl`。

同时把 API 健康检查改成 Python 方式，不再依赖容器里的 `curl`。

这一步学到的能力：

- 最小化镜像依赖
- 不是所有方便的命令都要装进容器

---

## 5.3 问题三：`pip install .` 失败

报错核心：

```text
ModuleOrPackageNotFoundError: No file/folder found for package agent
```

### 原因

`pyproject.toml` 里的项目名叫 `agent`，但仓库不是标准的可发布 Python 包结构。

换句话说：

- 项目适合“源码运行”
- 不适合直接 `pip install .`

### 解决方式

把 Dockerfile 的安装方式改成“直接安装依赖”，不再安装当前项目 wheel。

从：

```dockerfile
RUN pip install . fastmcp
```

改成：

- 使用仓库的 `requirements-commerce.txt` 安装当前依赖
- 然后继续用：

```dockerfile
CMD ["python", "-m", "uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

这一步学到的能力：

- 理解“源码运行型项目”和“可发布包项目”的区别
- 不是所有 Python 项目都适合 `pip install .`

---

## 5.4 问题四：pip 下载 PyPI 依赖超时

报错核心：

```text
HTTPSConnectionPool(host='files.pythonhosted.org', port=443): Read timed out
```

### 原因

容器构建时访问官方 PyPI 太慢。

### 解决方式

在 Dockerfile 里切换到阿里云 PyPI 镜像：

```dockerfile
ENV PIP_DEFAULT_TIMEOUT=120 \
    PIP_INDEX_URL=https://mirrors.aliyun.com/pypi/simple/ \
    PIP_TRUSTED_HOST=mirrors.aliyun.com
```

这一步学到的能力：

- Python 依赖源也可能成为部署瓶颈
- 镜像源和包源都要考虑网络环境

---

## 5.5 问题五：`dashscope` 缺失导致 API 重启

报错核心：

```text
ModuleNotFoundError: No module named 'dashscope'
```

### 原因

在手工写 Dockerfile 依赖时，漏掉了 `dashscope`。

`app/core/embeddings.py` 里有：

```python
import dashscope
```

### 解决方式

在 Dockerfile 的 pip 安装列表中补上：

```text
dashscope
```

这一步学到的能力：

- 容器能启动不代表依赖齐了
- 看日志定位缺什么模块很重要

---

## 5.6 问题六：`docker-compose` V1 的 `ContainerConfig` 错误

报错核心：

```text
KeyError: 'ContainerConfig'
```

### 原因

旧版 `docker-compose` V1 和当前 Docker Engine 组合会出兼容问题。

### 解决方式

安装 Compose V2，并改用：

```bash
docker compose up -d --build
```

这一步学到的能力：

- 工具版本兼容性是部署中的常见问题
- 不要执着在旧工具上死磕

## 7. 部署成功后做的进一步优化

部署完成后发现一个真实问题：

- 手机端页面很丑
- 输入区位置不合理
- 发送按钮不明显

于是继续做了移动端适配：

### 第一版优化

- 聊天区提到页面前面
- 输入区改成吸底
- 上传和发送按钮更明显

### 第二版优化

- 手机端改成“聊天主屏 + 设置抽屉”
- PC 端保持原来的双栏布局

这一步学到的能力：

- 部署成功只是开始，不是结束
- 线上体验问题也属于部署后的工作内容

## 9. 这次部署最值得记住的经验

### 经验 1：部署不是“执行命令”，而是“定位问题”

真正的部署能力，不是会背：

```bash
docker compose up -d --build
```

而是遇到错误后知道：

- 看哪里
- 改哪里
- 为什么这样改

### 经验 2：国内服务器要优先考虑镜像源和包源

常见问题不一定是代码错，而是：

- Docker Hub 太慢
- PyPI 太慢
- apt 源慢

### 经验 3：本地跑通不等于云上就能跑通

上云后会多出这些变量：

- 网络环境
- 操作系统差异
- 容器环境
- 端口与安全组
- 工具版本兼容

### 经验 4：先把系统跑通，再做体验优化

这次正确的顺序是：

1. 先让服务跑起来
2. 再看移动端体验
3. 再继续优化前端布局
